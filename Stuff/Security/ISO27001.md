## 🧩 What is ISO/IEC 27001?

**ISO/IEC 27001** is a certifiable standard for an **ISMS — Information Security Management System**. Read that as *management system*: it specifies the **process** by which an organization identifies risk, decides what to do about it, proves it did so, and improves. It is emphatically **not** a technical checklist, and it will never tell you which TLS ciphers to allow.

Think of it as **ISO 9001 for security** 🏭 — the auditor does not check whether your firewall is good; they check that you *decided* what "good" means, wrote it down, implemented it, measured it, and fixed what you found.

The division of labour: **27001** = the requirements you get audited against (clauses 4–10 plus the Annex A control list). **27002** = the implementation guidance explaining how each Annex A control actually works. You certify against 27001; you read 27002 while doing the work. (27005 covers risk management, 27017/27018 cloud and PII.)

---
## 💡 Why organizations do it

- **Procurement unblocking.** Enterprise, EU and Gulf tenders frequently list it as a hard requirement — no certificate, no bid.
- **One system, many frameworks.** The same risk register and controls feed SOC 2, [NIST CSF](./Cybersecutity%20Framework.md), GDPR Art. 32 and endless customer questionnaires.
- **Forcing function + accountability.** Someone finally owns the asset inventory, the access reviews and the incident register — and clause 5 puts security on management, not on the one engineer who happens to care.

---
## ⚙️ How it works — clauses 4–10 and the PDCA loop

Clauses 4–10 are the **auditable requirements**. Annex A is a *catalogue you select from*, not a to-do list.

| Clause | Name                       | What you must actually have                                              |
| ------ | -------------------------- | ------------------------------------------------------------------------ |
| **4**  | Context of the organization| The ISMS **scope**, interested parties, internal/external issues          |
| **5**  | Leadership                 | Signed policy, assigned roles, demonstrable management commitment         |
| **6**  | Planning                   | **Risk assessment + treatment plan**, the **SoA**, measurable objectives  |
| **7**  | Support                    | Competence, awareness training, documented information under control      |
| **8**  | Operation                  | Actually executing the risk assessment and treatment you planned          |
| **9**  | Performance evaluation     | Monitoring/metrics, **internal audit**, **management review**             |
| **10** | Improvement                | Nonconformities, corrective actions, continual improvement                |

This maps cleanly onto **PDCA**: Plan (4–7) → Do (8) → Check (9) → Act (10). Clause 9 is where unprepared organizations fail, because internal audit and management review must exist as **records with dates**, not intentions.

> [!NOTE]
> Amendment 1 (2024) added climate change to clauses 4.1/4.2 — you must now consider whether it is a relevant issue for the ISMS. A paragraph of work, not a project.

## 🗂️ Annex A in the 2022 revision — 93 controls, 4 themes

The 2013 edition had 114 controls in 14 clauses. **2022 restructured them into 93 controls across 4 themes**, mostly by merging duplicates rather than adding burden:

| Theme              | Ref | Controls | Examples                                                                  |
| ------------------ | --- | -------- | ------------------------------------------------------------------------- |
| **Organizational** | A.5 | 37       | policies, asset inventory, supplier security, cloud services, incidents     |
| **People**         | A.6 | 8        | screening, terms of employment, awareness training, disciplinary process    |
| **Physical**       | A.7 | 14       | secure areas, equipment siting, clear desk, physical monitoring             |
| **Technological**  | A.8 | 34       | access control, cryptography, secure development, logging, backup, network  |

Every control also carries **attributes** (control type, information security property, cybersecurity concept, operational capability, security domain), so the catalogue can be sliced by, for example, "all preventive controls in the *Protect* concept". The **11 genuinely new** controls below are the ones worth memorising — they are exactly where a 2013-era ISMS fails its transition audit:

| New control                                     | Ref    | What it actually asks of engineering                              |
| ----------------------------------------------- | ------ | ----------------------------------------------------------------- |
| **Threat intelligence**                         | A.5.7  | Consume advisories/feeds *and act on them* — not just subscribe     |
| **Information security for use of cloud services** | A.5.23 | Own the shared-responsibility split, per provider, in writing    |
| **ICT readiness for business continuity**       | A.5.30 | RTO/RPO that have actually been tested, not aspirational            |
| **Physical security monitoring**                | A.7.4  | Alarms, CCTV, access logs on secure areas                          |
| **Configuration management**                    | A.8.9  | Hardened baselines under version control — IaC counts               |
| **Information deletion**                        | A.8.10 | Retention limits enforced in code, plus proof of deletion           |
| **Data masking**                                | A.8.11 | No production PII in staging or in a developer's local dump         |
| **Data leakage prevention**                     | A.8.12 | DLP on the egress paths: email, endpoints, object storage           |
| **Monitoring activities**                       | A.8.16 | Detection with alerting *and* somebody on the other end             |
| **Web filtering**                               | A.8.23 | Control which external sites systems and staff can reach            |
| **Secure coding**                               | A.8.28 | Standards, code review, SAST/SCA in CI, dependency hygiene          |

## 📋 Risk assessment, treatment, and the Statement of Applicability

1. **Identify risks** to confidentiality, integrity and availability of in-scope information (see [CIA](./CIA.md)). Asset-based or scenario-based is your choice, but the method must be documented and repeatable.
2. **Analyse and evaluate** each risk against defined criteria and compare it to your stated risk acceptance level.
3. **Treat** it — **mitigate** (apply controls), **transfer** (insurance, supplier), **avoid** (stop doing it) or **accept** (with a named owner).
4. **Produce the SoA** and the risk treatment plan; the **risk owner** signs off residual risk in writing.

The **Statement of Applicability** is the spine of the certification. For all 93 Annex A controls it records: applicable or not, **why**, and current implementation status. It matters because:

- It is the auditor's map — Stage 2 is largely "show me the evidence for what your SoA claims". Exclusions are legitimate but must be **justified** ("fully cloud-hosted, no owned datacentre, A.7.x handled by the provider"); an unjustified exclusion is a nonconformity.
- Claiming a control is implemented when it is not is the fastest route to a **major** finding.

## 🏅 The certification path

| Step                          | What happens                                                                                     | Timing              |
| ----------------------------- | ------------------------------------------------------------------------------------------------ | ------------------- |
| **Readiness / gap analysis**  | Optional; internal or consultant-led                                                              | before committing    |
| **Stage 1 audit**             | *Documentation* review — scope, policy, risk assessment, SoA, internal audit records. Are you ready? | 1–2 days          |
| **Stage 2 audit**             | *Implementation* audit — evidence, sampling, interviews with the engineers who do the work         | 3–10 days           |
| **Certificate issued**        | Valid **3 years**, from an **accredited** body (UKAS, ANAB, …)                                     | after findings close |
| **Surveillance audits**       | Annual, partial scope                                                                             | years 1 and 2        |
| **Recertification**           | Full audit again                                                                                  | year 3               |

Findings are **minor** (fix under a corrective action plan) or **major** (blocks certification until resolved). You must have completed at least one **internal audit** and one **management review before Stage 2** — an ISMS that has never run its own loop cannot be certified. Also verify the body is accredited: an unaccredited "certificate" fails customer due diligence anyway.

## 🧪 Example — the evidence an engineer is actually asked for

Auditors do not read your code, they sample **records**. Generate them continuously; do not reconstruct them the week before.

```bash
# A.5.15 / A.5.18 access review - who has what, and who stopped showing up
python manage.py shell -c "
from django.contrib.auth import get_user_model
import csv, sys
w = csv.writer(sys.stdout)
w.writerow(['username', 'is_staff', 'is_superuser', 'groups', 'last_login'])
for u in get_user_model().objects.all().order_by('username'):
    w.writerow([u.username, u.is_staff, u.is_superuser,
                '|'.join(g.name for g in u.groups.all()), u.last_login])
" > evidence/2026-Q3-access-review.csv
# A.8.13 backup - the evidence is a RESTORE, not a dump file that exists
pg_dump -Fc -d prod > /backups/prod-$(date +%F).dump
createdb restore_test && pg_restore -d restore_test /backups/prod-$(date +%F).dump
psql -d restore_test -c "select count(*) from orders;"   # record count + date
```

| The ask                | Evidence that satisfies it                                                          |
| ---------------------- | ----------------------------------------------------------------------------------- |
| Access control         | Quarterly access-review export, signed off by the system owner                       |
| Change management      | PR → ticket → approval → deploy, traceable in both directions                        |
| Logging & monitoring   | Retention config, an alert that actually fired, and what someone did about it         |
| Backups                | A **restore test** record with a date and a row count                                 |
| Joiner/mover/leaver    | Dated checklist per person; accounts disabled inside the stated SLA                   |
| Supplier security      | A review per third party: their cert/SOC 2, the DPA, what data they hold              |
| Secure development     | Code review records, SAST/[SCA](../Hardening/SCA.md) reports, [threat models](./ThreatModeling.md) |

## ⚖️ ISO 27001 vs NIST CSF vs SOC 2 vs PCI DSS vs GDPR

| Framework                                      | Nature                                          | Scope                                   | Who demands it                              | What you hand over                                              |
| ---------------------------------------------- | ----------------------------------------------- | --------------------------------------- | ------------------------------------------- | --------------------------------------------------------------- |
| **ISO 27001**                                  | **Certifiable** international standard (an ISMS) | The whole management system, as scoped   | Enterprise / EU / Gulf procurement, tenders  | A 3-year certificate + ISMS records (SoA, risk register, audits) |
| **NIST CSF 2.0**                               | **Voluntary framework**, not certifiable         | Risk outcomes across 6 functions         | Nobody contractually; boards and US agencies | A Current vs Target profile and a gap plan                       |
| **SOC 2**                                      | **Attestation report** by a CPA firm (AICPA TSC) | Controls at a service org over a period   | US SaaS buyers, vendor security reviews       | A Type I/II report shared under NDA                             |
| **PCI DSS**                                    | **Contractual mandate** from the card brands     | Only the cardholder data environment      | Acquirers/brands, if you touch card data      | SAQ or ROC + AOC, quarterly ASV scans                            |
| **GDPR**                                       | **Law** (EU regulation)                          | Personal data of EU/EEA data subjects     | Regulators, DPAs, and data subjects           | RoPA, DPIAs, lawful basis, 72-hour breach notification           |

ISO 27001 proves you *manage* security; SOC 2 proves controls *operated* over a period; PCI DSS is a technical checklist for one system; GDPR is law you cannot opt out of; NIST CSF is how you organize the work. [NIST CSF](./Cybersecutity%20Framework.md) is already covered separately in this vault — its Informative References map straight onto Annex A, which is why one control set can serve both.

## 🚨 When NOT to pursue certification

- ❌ **Pre-product or pre-revenue.** There are no processes to certify yet, and it costs 6–12 months plus real money. Do the controls now, the certificate when a deal needs it.
- ❌ **When the customer only actually wants SOC 2.** Ask which artifact unblocks the deal. US buyers usually want a SOC 2 Type II report; shipping them an ISO certificate solves nothing.
- ❌ **When certification becomes theatre.** A scope drawn as "the marketing website" passes the audit and protects nothing. A certificate is evidence of a *process*, never proof that a system is secure — no auditor will find your IDOR, so certification and [threat modeling](./ThreatModeling.md) / testing are complementary, and only one of them finds bugs.

## 🔐 Security notes & production hardening

- **Automate the evidence, or it will not exist.** Access-review exports, restore-test logs and deploy→ticket links should fall out of CI and cron, not out of a panic sprint before Stage 2.
- **Scope honestly.** A narrow scope is cheaper to certify and worthless to a customer who then finds their data is outside it. Expect to be asked exactly that question.
- **Secrets are the control everyone fails.** Credentials in `settings.py`, in CI variables printed to logs, or in a `.env` committed years ago. Centralise into [Vault](../DevOps/Vault/README.md) with rotation and an audit device.
- **Retention is a two-way risk.** Logs too short and you cannot investigate; PII kept too long and you breach A.8.10 and GDPR at once. Write the number down and enforce it in code. And **never fake evidence** — a backdated access review is a *major* nonconformity and, after a breach, evidence of negligence. "Not implemented, risk accepted by \<owner\>" is a perfectly acceptable answer.

## 🐍 Controls that map to daily backend work

| Annex A control                                    | What it looks like in your repo                                                                          |
| -------------------------------------------------- | -------------------------------------------------------------------------------------------------------- |
| **A.8.24** cryptography, **A.8.20** networks        | TLS everywhere, disk/column encryption, no plaintext hops → [Transport Security](./TransportSecurity.md)   |
| **A.5.15–A.5.18** access control                    | Deny-by-default permissions, object-level checks, quarterly reviews → [Access Control](./AccessControl.md) |
| **A.8.28** secure coding, **A.8.8** vulnerabilities | Code review, `pip-audit`, [SCA](../Hardening/SCA.md) in CI, a written patch SLA                            |
| **A.8.15/A.8.16** logging & monitoring              | Structured logs, defined retention, alerts that actually page a human                                     |
| **A.8.13** backup, **A.5.30** ICT readiness         | Restore tests with records; RTO/RPO you have genuinely measured                                            |
| **A.8.11** masking, **A.8.10** deletion             | No production PII in staging; retention jobs that really delete rows                                       |

Practically all of this is work you would do anyway — ISO 27001's contribution is forcing you to *record* that you did it, with a date and an owner.

## 🧠 Summary

| Concept                | Takeaway                                                                                  |
| ---------------------- | ----------------------------------------------------------------------------------------- |
| **ISO 27001**          | A certifiable **management system** for security: process, not a technical checklist        |
| **27001 vs 27002**     | 27001 is the requirements you are audited against; 27002 explains how to implement them     |
| **2022 Annex A**       | **93 controls, 4 themes**, 11 new ones (cloud, threat intel, secure coding, DLP, masking…)  |
| **The SoA**            | Applicable / not / why / status for all 93 — the document the whole audit runs on            |
| **Certification**      | Stage 1 docs → Stage 2 implementation → 3-year certificate + annual surveillance             |
| **The honest caveat**  | A certificate proves a managed process, never that the system is secure                      |
